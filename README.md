# prado-cabrero.com — Pelican site

Your WordPress/Divi site rebuilt as a Pelican static site. Write in
Markdown, run one command, get plain HTML. Same design as before,
one stylesheet for the whole site.

---

## Quick start

```bash
pip install -r requirements.txt

# Preview locally at http://localhost:8000
pelican content -s pelicanconf.py -l

# Build the real site into output/ for publishing
pelican content -s publishconf.py
```

---

## Publishing a new article

1. Create `content/articles/my-new-article.md`
2. Fill in the metadata block at the top (copy it from an existing file)
3. Write the body in Markdown
4. Run the build
5. Commit and push

The home page, the RSS feed, and the sitemap all update themselves.
**You never edit a template to publish a post.**

### Metadata fields

```
Title: Which omega-3s are essential?
Date: 2025-10-25 10:00
Slug: which-omega-3s-are-essential   <- becomes the URL. Never change it after publishing.
Author: Alfonso Prado-Cabrero, PhD
Kicker: Essential Fatty Acids — Explainer   <- small label above the title
Dek: One-sentence subtitle.                 <- also used on the home page card
Image: hero.jpg                             <- hero image, in content/images/
Image_alt: Flaxseed
Image_credit: Photo by <a href="...">Name</a>.
Card_image: thumbnail.webp                  <- home page thumbnail (falls back to Image)
Summary: Used for the meta description and social previews.
```

### Writing the body

Plain Markdown. `## Heading`, `*italic*`, `[text](url)`.

- **Images and animated GIFs**: put the file in `content/images/`,
  then write `![alt text](/images/my-animation.gif)`
- **Callout box** (the highlighted grey panel): use a blockquote, `> your text`
- **References**: wrap them as shown in `which-omega-3s-are-essential.md` —
  a `<section class="references" markdown="1">` around a normal numbered
  list. The `[1] [2] [3]` markers are generated by CSS, not typed.

## Project layout

```
content/
  articles/     your blog posts (.md)
  pages/        standalone pages: About, Projects, Publications, Hobbies
  images/       photos, GIFs, logo, icons  ← YOU NEED TO FILL THIS
  extra/        CNAME (custom domain) and robots.txt
theme/
  templates/
    base.html     shared: head, masthead, nav, footer  ← edit nav here once
    article.html  a single blog post
    index.html    home page (builds the article list automatically)
    page.html     standalone pages
    sitemap.html  generates sitemap.xml, no plugin needed
  static/css/
    style.css     ALL styling for the whole site
pelicanconf.py    settings (nav links, bio, licence)
publishconf.py    production settings (real domain, RSS on)
output/           generated site — this is what gets published
```

## Deploying to GitHub Pages

```bash
# One-time
git init
git remote add origin https://github.com/YOURNAME/prado-cabrero.com.git

# Each time you publish
pelican content -s publishconf.py
git add -A && git commit -m "New article" && git push
```

Then in the repo settings, enable Pages and point it at the branch
holding `output/`. The simplest arrangement is a separate `gh-pages`
branch — `pip install ghp-import` then `ghp-import -b gh-pages -p output`
does it in one command.

For the custom domain: `content/extra/CNAME` already contains
`prado-cabrero.com` and lands at the site root on every build, so it
won't get wiped. Point your DNS at GitHub's IPs and enable
"Enforce HTTPS" in the repo settings.

### After going live

- Submit `https://prado-cabrero.com/sitemap.xml` to Google Search Console
- Watch the Coverage report for a few weeks for unexpected 404s
- Keep SiteGround running for a month before cancelling

## Things that did NOT come across from WordPress

- **Cookie consent banner** — a plugin. A static site with no analytics
  and no tracking cookies usually doesn't need one. If you add analytics
  later, revisit this.
- **Contact forms, comments, search** — all need a server. There are
  static-friendly alternatives (Formspree, Pagefind) if you want them.
- **Email at your domain** — GitHub Pages doesn't do email. If you use a
  `@prado-cabrero.com` address through SiteGround, keep that service or
  move it elsewhere.

## Importing your existing content (Divi users: read this)

The WordPress XML export is **not usable directly** for a Divi site.
Divi stores articles as shortcodes (`[et_pb_section]`, `[et_pb_text]`),
so the export gives you shortcode soup — and it duplicates whole
articles inside attributes like `content_tablet="..."`.

Use `tools/import_from_live_site.py` instead. It reads the *rendered*
pages from your live site, where Divi has already turned the shortcodes
into clean HTML, and converts those.

```bash
pip install requests beautifulsoup4 markdownify
python tools/import_from_live_site.py
```

Run it from the project root. It writes `.md` files into
`content/articles/` and `content/pages/`, and downloads every image
into `content/images/`.

The list of pages to import is at the top of the script — edit it there.
The Spanish versions and older project pages are listed but commented
out; uncomment any you want to keep.

**Afterwards**, open each generated file and check it. Automated
conversion gets ~95% right; expect to fix a stray caption or move a
figure. In particular:

- Shorten the `Dek:` line if the meta description was long
- Wrap the reference list in
  `<section class="references" markdown="1"> ... </section>`
  so the `[1] [2] [3]` styling applies
- Confirm the `Slug:` matches your live WordPress URL exactly
